# Test oracles, APIs and evidence

Read the exact Swift import and target annotations before using unfamiliar APIs; Objective-C constant spelling is not the Swift member name. Inspect completed diagnostics before repairing. Keep first source, scaffold and outcome separately. Keep owners alive in callback tests; use native-only controls and appropriate autorelease boundaries before claiming a leak. Mutants must affect the active platform branch and fail the intended assertion: build failures or unchanged branches are not successful rejections. Pure policy, native getters/dispatch, compilation and actual interaction are different evidence. Accept valid alternative code and no-code no-change answers. Suggest focused compile/unit checks without imposing manual/UI gates.

Use only for this concern. Apply Apple source/SDK contracts to the actual target; examples and application policies are not universal platform guarantees.

A regression question must describe the developer’s task, not the known repair. Keep rubric, expected routes and incident outputs outside model input. A valid alternative satisfying the same observable contract must pass.
